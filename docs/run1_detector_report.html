Detector Run 1 — what came back

The first real training run of the side-scan-sonar object detector is done. One class works well, one looks perfect for the wrong reason, three are weak. Here is the plain-language readout, the fixes going into Run 2, and how the confidence and geotagging modules get built next.

Model YOLOv8s (box detection) Classes 5 Epochs 120 Train time 2.5 h · RTX 4050 Speed 3.9 ms / frame Date 2026-08-31

The short version

Pipeline detection genuinely works — 0.98 AP50 on held-out real sonar, near-perfect recall. That is a real, defensible result and it is our lead story.

Ghost-net's 0.99 is not real. That class has no real training data — train and test are both procedurally generated by the same script, so the model just re-recognises its own synthetic pattern. It is a shape proof-of-concept, never a field number.

Crab-pot failed (0.12 AP50, finds under 1 in 4). Shipwreck and cylinder are weak (~0.44, ~50% recall). All three causes are self-inflicted and fixable.

This is a checkpoint, not the finish. One more retrain with data fixes, then Module 1 is locked and the team moves to Modules 2–4.

01 What we actually trained

A detector looks at a sonar image tile and draws a labelled box around each man-made object it finds, with a raw score. We are doing boxes, not pixel-perfect outlines — the problem statement allows either, and every real sonar dataset we could get is box-labelled.

05 What changes for Run 2

Every failure above traces to a data decision we made, not to the model. Fixes already applied to build_dataset.py; splits are rebuilt and ready.

  • Crab-pot data nearly doubled — 900 → 1,600 training images (of ~5,700 available). It was starved.
  • Dropped the weak shipwreck crops — the KLSG "whole frame is the object" boxes taught it "big blob = wreck", which caused the rock-cluster false alarms. Shipwreck now uses only tightly boxed sources.
  • Cylinder + background topped up — 350 extra synthetic cylinders, 500 background tiles (was 400).
  • Ghost-net unchanged — still synthetic, still labelled as such everywhere.

Decision rule after Run 2 — then Module 1 is locked, no third attempt:

  • crab-pot AP@50 ≥ 0.35 → keep all 5 classes.
  • crab-pot AP@50 still < 0.25 → ship 4 classes (drop crab-pot). Pipeline + shipwreck + cylinder + net map exactly onto the hazards the problem statement names, which is a cleaner pitch than 5 classes carrying a broken one.

07 Module 2 — Confidence Scoring & Noise Filtering

What the problem statement asks: minimise false positives from natural acoustic shadows and rock clusters, and output a clear 0–100% confidence score for every detection.

Our approach — three stages after the detector, no second neural network:

  1. De-duplicate (NMS)

    Merge overlapping boxes that describe the same object, keeping the strongest. Standard, already in the detector output path.

  2. Calibrate the score → real probability

    A raw detector score of "0.8" is not an 80% chance of being right — neural nets run over-confident. We fit a one-parameter logistic curve (Platt scaling) on the validation set that maps raw score → observed hit rate. Output is the honest 0–100% the problem statement wants. Quality is measured by Expected Calibration Error and shown as a reliability diagram (predicted vs actual, should sit on the diagonal). Code stub: ml/scripts/calibrate_confidence.py.

  3. Shadow-geometry check → demote physics violations

    This is the anti-false-alarm step, and it is pure geometry — no training needed. A real raised object on the seabed casts an acoustic shadow whose length is fixed by the sonar's height, its range, and the object's own height. A rock cluster gives a strong return but its shadow does not match what geometry predicts. If a detection's measured shadow is inconsistent, its confidence is knocked down regardless of how bright the return was. Code stub: ml/inference/shadow_verification.py.

Deliverables

  • Calibrated 0–100% score on every detection, wired into ml/inference/confidence_filter.py.
  • Calibration quality: ECE number + reliability diagram for the deck.
  • False-positive rate before vs after the shadow check, measured on the background tiles and the unused Roboflow / KLSG seabed imagery as a hard-negative set.

08 Module 3 — Reporting & Geotagging Engine

What the problem statement asks: read sonar metadata (coordinate files or ping headers) and output a structured JSON/CSV report giving each hazard's latitude/longitude, size, and class.

Our approach:

  1. Parse the navigation metadata

    Side-scan sonar logs (XTF format) carry per-ping headers: position fix, heading, altitude, range scale, timestamp. Where a raw log has no embedded fix, a sidecar navigation CSV provides it. Parsers: backend/geotagging/xtf_reader.py, metadata_parser.py. Real test fixture: the AURORA dataset, which ships a real navigation.csv + XTF pair.

  2. Project each detection from pixels to Earth coordinates

    A detection sits at some (row, column) in a sonar tile. Row → ping number → timestamp → the vehicle's position and heading at that instant. Column → slant range → true distance across the seabed (corrected for altitude) → offset left/right of the track. Combine and you get absolute lat/lon for the hazard. Box width/height convert to metres the same way. Math: backend/geotagging/coordinate_projection.py.

  3. Emit the structured report

    One record per hazard in the locked schema (backend/reporting/schema.py): id, source file, ping id, timestamp, lat, lon, class, calibrated confidence, box geometry, review status. Exported as both JSON and CSV. Every record keeps a pointer back to its source ping for audit.

Deliverables

  • XTF + navigation-CSV parser, validated on the AURORA fixture.
  • Pixel→lat/lon projection, checked against AURORA's known fixes.
  • JSON and CSV export matching schema.py, one row per hazard, with audit pointers.
