01

The problem is the shadow, not the object

Problem Statement 26057 asks for automated detection of shipwrecks, pipelines, cylinders and ghost nets in side-scan sonar. The difficulty is not that debris is small. It is that sonar does not photograph a scene — it measures echoes.

A side-scan image is built from acoustic backscatter. Many scatterers inside one resolution cell return echoes that add with random phase, so the noise is multiplicative, not additive: I_obs = I_true · n. Blur it away with an averaging filter and you destroy the very edges that carry meaning.

And an object's identity lives as much in its shadow as in its bright return. A wreck standing proud of the seabed occludes the beam behind it and casts a dark trail whose length is fixed by geometry. A rock cluster returns just as strongly — but sits nearly flush, so it casts almost nothing. That single difference is what separates a hazard from a false alarm, and it is the basis of our false-positive filter.

02

Choosing the detector under an edge budget

The system has to run on or near an AUV — no cloud, no datacentre GPU. That constraint eliminated most of the field before accuracy entered the conversation.

ArchitecturemAP@50FPSSizeVerdict for an AUV

RT-DETR (transformer)0.74128.586 MB16× the size for +0.01
YOLO family0.75540.15.25 MBbest accuracy, near-best speed, tiny

Those are published figures, all measured on AI4Shipwrecks — the same dataset behind our shipwreck class (Lin et al., Scientific Reports 2026). They are not our claims; they are the independent evidence that a YOLO-family detector is the correct choice for this task, not merely a convenient one.

We chose YOLOv8s specifically: 11.8 M parameters fits a 6 GB laptop GPU at batch 16, and its export path to ONNX and TensorRT is mature — newer YOLO variants routinely emit operations that edge compilers cannot yet consume. It is also anchor-free, which removes the k-means anchor-tuning step earlier sonar work needed.

A trade-off we declined

Two independent papers report that bolting attention modules onto YOLOv8 buys roughly +5 mAP at the cost of ~30 % of the frame rate (DFSE-YOLO: 37.9 → 26.5 FPS; Jiang et al. 2024: 89 → 61 FPS). For a vehicle-borne system that is the wrong side of the trade. We took the zero-cost improvements and left the attention blocks on the roadmap.

03

The data did not exist, so we assembled it

There is no public dataset of ghost nets in side-scan sonar. None. A Microsoft AI for Good / WWF programme working on exactly this problem had 412 real annotated segments in total and described its own work as a feasibility study.

So the training set was built one class at a time from six real surveys, with procedural synthesis used only where reality offers nothing. 6,405 tiles — 4,775 train, 780 validation, 850 held-out test.

The rule we held to: synthetic data is a specialist filler, never a substitute. The literature supports the caution — Qin et al. (2021) showed synthetic augmentation actively hurts when it does not match the real feature distribution, and Du et al. (2025) found the benefit plateaus by roughly 1,000 images per class. Beyond that point you are buying volume, not information.

04

Three runs, and what each one bought

The model did not arrive correct. Each run isolated a specific failure and paid for a specific fix — which is what makes the progression evidence rather than anecdote.

Run 1 → Run 2 — killing the false alarms

Dropped the KLSG shipwreck labels. Cropped ship photos had been given a full-frame box, teaching the model that any large blob is a wreck. It was the rock-cluster false-alarm engine.
False-positive rate 0.313 → 0.266
shipwreck precision 0.57 → 0.66
Doubled crab_pot data (900 → 1,600 tiles) to rescue the failing class, and rebuilt the splits to 80/10/10 with per-class caps.
crab_pot AP 0.118 → 0.193
still far below the 0.25 bar

The decision that took discipline

Two runs and a doubling of data moved crab_pot from 0.118 to 0.193. That is not a data-volume problem, it is a separability problem — the class is small, low-contrast and acoustically ambiguous. We kept it in training as a hard negative and filtered it out of the product. The four classes that ship are exactly the four hazards the problem statement names.

Run 2 → Run 3 — fixing the data pipeline

Re-tiled AI4Shipwrecks with 50 % overlap plus a morphological close so a broken hull reads as one object. The original stride threw away ~90 % of the usable data.
152 → 890 tiles · 329 → 1,978 boxes
shipwreck instances 75 → 1,554
Added a Lee speckle filter + CLAHE front end (Module 0), applied identically at training and at inference so the model never sees an unfamiliar distribution.
precision 0.734 → 0.734
FP rate 0.266 → 0.266 — no change

A negative result we kept anyway

On a matched protocol the preprocessed and raw models are statistically indistinguishable: identical precision, identical false-positive rate, mAP within noise. The detector learns an equivalent denoising internally once augmentation is strong enough. We report it because a clean negative result is worth more than a flattering one — and we kept the preprocessing only because CLAHE'd input measurably improves shadow detectability, which Module 2 depends on.

05

Reading the training honestly

120 epochs, batch 16, 640 px, on a laptop RTX 4050 in 2.1 hours. The curves show something worth stating plainly rather than hiding.

Why shipwreck AP fell while the model got better

The 50 % overlap re-tile that gave us 12× more shipwreck training data also tripled the shipwreck instances in the test set, adding partial and near-duplicate tiles. The test became harder at the same moment the model got stronger.

The control settles it: running the Run 2 model on the Run 3 test set scores shipwreck 0.278 — below the new model's 0.302. On matched data the two are tied, and Run 3 is marginally ahead.

Overall on the held-out test set: mAP@50 0.641 · mAP@50-95 0.459 under the standard protocol, and precision 0.734 · recall 0.629 at the operating threshold an analyst actually sees.

Two protocols, and why both belong here

mAP is the area under the whole precision–recall curve, so it is computed with the confidence floor at ~0.001 — the COCO convention every paper in §08 uses. Precision and recall are operating-point numbers, meaningful only at the threshold actually deployed (0.25 here, ahead of Module 2’s per-class gate).

We had been reporting mAP computed at conf 0.25, which truncates the curve’s low-confidence tail and mechanically depresses AP. Same model, same test set: mAP@50 0.580 → 0.641, shipwreck 0.302 → 0.370, cylinder 0.424 → 0.517. The corrected figures are the ones comparable to published work. The run-to-run comparisons in §04 were all measured identically, so that progression is unaffected.

A detection is not a probability

A raw sigmoid output of 0.8 is not "right 80 % of the time". We fit per-class Platt scaling on held-out data so the number the operator sees means what it says. Per-class matters: a single global calibrator made things measurably worse.

Combined with a per-class confidence gate, this is what converts raw detections into an operator product: shipwreck precision 0.63 → 0.73 and cylinder 0.58 → 0.75 at the working threshold, with scores that survive scrutiny.

07

Making it fit on a vehicle

An AUV has no GPU and no room for a 1.5 GB PyTorch runtime. We exported to ONNX and measured all three precisions rather than assuming.

INT8 ONNX11.5 MB164 ms — slower0.00 precision / 0.00 recall, every classexcluded

Where we went past the literature

The 2026 paper that sets the AI4Shipwrecks detection record assumes INT8 quantization transfers cleanly, with "proportional" reductions. We tested it. On faint sonar targets, static post-training quantization collapsed the detector to zero — and was slower than FP32 on any CPU without VNNI/AVX-512, because the quantise/dequantise nodes cost more than the integer math saves.

We publish the broken INT8 file alongside the working ones so the result is reproducible. This is the kind of finding you only get by measuring what everyone else assumes.

The deployment path carries no PyTorch at all — onnxruntime + numpy + opencv, roughly 50 MB resident against ~1.5 GB just to import torch. Verified: a shipwreck tile scores 91.3 %, auto-confirmed, in 110 ms, with torch and ultralytics both absent from sys.modules. At ~11 tiles/second against a sonar producing a few pings per second, the model is comfortably faster than the sensor.

08

Does it hold up against the field?

The obvious challenge to our work is the shipwreck number. Answering it requires knowing what "good" means for this task — and two 2026 papers benchmark the same dataset we train on.

Three things follow, and each is a defensible claim rather than a hopeful one:

  • Our all-class mAP@50 of 0.641 sits within 0.08 of the single-class state of the art — while carrying four hazard types in one set of weights instead of one. On shipwreck alone we reach 0.370; the remaining gap is multi-class dilution plus a harder overlapping split, and a calibrated 50 px box-merge, already identified from the literature, is the named route to close it.
  • Pipeline detection at 0.98 exceeds anything in this comparison. The classes with abundant real data are solved; the weak classes are weak for a data reason we can point at.
  • The evaluation methodology is defensible. Following GhostVision (2026) — which showed a best-mAP model with 0.6 % precision — we report calibrated precision, recall and expected calibration error at the actual operating point, not just a threshold-averaged mAP.

Every limitation below is measured, and every one has a known remedy. Stating them is cheaper than being caught by them.

Where the next gain comes from

The training curve says the model is data-limited, not capacity-limited. So the roadmap is not a bigger network — it is a calibrated box-merge for fragmented hulls (published, + cross-validated at F1 0.87), temporal persistence across overlapping tiles to kill one-off false positives, and a fine-tuning loop that turns an operator's own sonar into training data. Selective deep-feature enhancement — 0.755 mAP at 40 FPS in 5 MB — is the version-two accuracy path, and its code is public.
