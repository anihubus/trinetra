Part I — the problem
01

The problem statement, decoded

PS 26057 (Ministry of Earth Sciences / NIOT) asks for an AI-powered automated underwater marine debris and anomaly detection system using side-scan sonar imagery. Eight functional requirements. Here is each one, and where it lives in what we built.

The scenario this replaces

Researchers tow sonar behind boats to build acoustic maps. A single survey vessel maps roughly 130 hectares a day, and every metre of it currently gets reviewed by a human scrolling through kilometres of grey imagery. It is slow, tedious, and error-prone in the specific way fatigue is error-prone — the misses cluster at the end of the shift.

The system's job is not to replace the analyst. It is to filter out the empty seafloor so the analyst reviews only the flagged segments. That reframing decides the entire design: recall matters, but a system that floods the queue with false alarms has not saved anyone any time. Which is why Module 2 exists at all.

02

Why sonar is not photography

Every downstream decision follows from one fact: a side-scan image is not a picture of the seabed. It is a map of how sound came back.

The tow-fish emits a pulse and listens. Each ping is one cross-track line, sampled in slant range — round-trip travel time × sound speed ÷ 2. Stack the pings as the vehicle advances and you get the familiar waterfall. Three consequences shape everything:

  • Speckle is multiplicative. Many scatterers inside one resolution cell return echoes that add with random phase, so I_obs = I_true · n. This is not sensor noise you can average away — an averaging filter destroys the edges that carry the signal.
  • Brightness falls with range. Acoustic energy spreads and is absorbed, so the same object looks bright at 5 m and washed out at 30 m. Without correction, a model learns range, not objects.
  • The shadow is half the information. A raised object blocks the beam behind it. The dark trail is not an artefact — its length is fixed by geometry, and it is often the only thing separating a hazard from a rock.

Each hazard class has a distinct acoustic signature

This is why a single detector treating all four classes identically would be the wrong design, and why our per-class thresholds and per-class calibrators are not a convenience but a requirement.

Collecting data that does not exist

The problem statement names four hazards. Public labelled side-scan data exists for exactly one of them.

Target classPublic data situationWhat we did

So the training set was assembled one class at a time from six real surveys, with procedural synthesis used only where reality offers nothing. Final: 6,405 tiles — 4,775 train, 780 validation, 850 held-out test, at 640 × 640.

The rule we held to

Synthetic data is a specialist filler, never a substitute. The literature is unambiguous on the risk: Qin et al. (2021) showed synthetic augmentation actively hurts when it does not match the real feature distribution, and Du et al. (2025) found the benefit plateaus by roughly 1,000 images per class. Past that point you are buying volume, not information.

So ghost_net is 100 % synthetic because nothing real exists, mine_cylinder gets a small top-up, and every other class is real survey data or nothing.

One data fix mattered more than any hyper-parameter

Our first pass fed each ~5,600-px AI4Shipwrecks transect strip in whole, so "one wreck" became one enormous box — 141 strips yielded only 152 usable tiles. Re-tiling at 50 % overlap with a morphological close (so a broken hull reads as one object) took that to 890 tiles and 1,978 boxes. Shipwreck training instances went 75 → 919 → 1,554 across the three runs. No amount of tuning would have substituted for that.

04

Preprocessing — the full pipeline and what we shipped

The complete acoustic preprocessing chain has six stages. We implemented four and ship two. The reason for the gap is architectural, not a shortcut — and it is worth stating precisely.

The two operators we ship

Lee filter — a local linear minimum-mean-square-error estimate. In a window around each pixel it forms the local mean μ and variance σ², then outputs:

Lee (MMSE) updateÎ(x) = μ + W · ( I(x) − μ )     W = σ²signal / ( σ²signal + σ²noise )

On flat seabed the local variance is almost all noise, so W → 0 and the output is the smoothed mean. On an edge it is dominated by real structure, so W → 1 and the pixel survives untouched. Edge-aware by construction — which matters because the edges are the shadows.

CLAHE — histogram equalisation lifts faint contrast, but done globally it also amplifies speckle in flat sand. CLAHE equalises per 8×8 tile with a clip ceiling that caps the local gain, so a faint wreck edge is boosted while flat-sand speckle is not. It is also the direct answer to acoustic path loss: near-range brightness comes down, far-range comes up, and the same object looks the same at 5 m and 30 m.

The negative result we published anyway

We ran the ablation properly: same data, same protocol, preprocessed vs raw. The models are statistically indistinguishable — identical precision (0.734), identical false-positive rate (0.266), mAP within noise. With strong training-time augmentation, the detector learns an equivalent internal denoising.

We kept the preprocessing anyway, for one measured reason: CLAHE'd input makes acoustic shadows more separable, which is what Module 2's geometry check consumes. A clean negative result is worth more than a flattering one, and it tells us where not to spend the next week.

What the literature settles, in eight lines

  • Our shipwreck number is at state of the art, not below it. Single-class YOLO on a clean AI4Shipwrecks split tops out at 0.72–0.76; annotators agree only 50–60 %.
  • COCO→sonar transfer learning is established practice — four independent SSS studies. From-scratch plateaus near 80 % accuracy.
  • Dropping KLSG was right — independently confirmed as a weak transfer source.
  • mAP alone misleads. Report the operating point.
  • Cross-survey transfer requires fine-tuning — documented field-wide, with the same remedy we propose.
  • Synthetic data helps only when it matches the real distribution, and plateaus by ~1000/class.
  • Attention modules cost ~30 % frame rate — two independent sources. Wrong trade for a vehicle.
  • Human-in-the-loop review is proven design, not a fallback.
Part IV — the model
06

Choosing the detector

The edge requirement eliminated most of the field before accuracy entered the conversation. These are published figures, all measured on AI4Shipwrecks — not our claims.

ArchitecturemAP@50FPSSizeVerdict for an AUV
Faster R-CNN0.73212.4108 MBtwo-stage — too slow
SSD0.65442.092.6 MBfast, weakest accuracy
RT-DETR (transformer)0.74128.586 MB16× the size for +0.01
YOLO family0.75540.15.25 MBbest accuracy, near-best speed, tiny

YOLOv8s specifically: 11.8 M parameters fits a 6 GB laptop GPU at batch 16, and its export path to ONNX and TensorRT is mature — newer YOLO variants routinely emit operations edge compilers cannot yet consume. It is anchor-free, removing the k-means anchor-tuning step earlier sonar work needed.

Boxes, not masks. The PS accepts either. Every real SSS dataset we could obtain is box-labelled; the only pixel masks (AI4Shipwrecks) come with a published benchmark we cite for the segmentation roadmap. Boxes now, masks as a documented v2.

A trade-off we declined, twice-confirmed

Bolting attention modules onto YOLOv8 buys roughly +5 mAP at the cost of ~30 % of the frame rate — DFSE-YOLO 37.9 → 26.5 FPS, Jiang et al. 89 → 61 FPS. For a vehicle-borne system that is the wrong side of the trade. We took the zero-cost improvements and left the attention blocks on the roadmap, where DFSE-YOLO's selective application (deep layers only) is the code-available path that recovers the speed.

07

Three runs, and what each one bought

The model did not arrive correct. Each run isolated a specific failure and paid for a specific fix — which is what makes the progression evidence rather than anecdote.

Run 1 → Run 2 — killing the false alarms

Dropped the KLSG shipwreck labels. Cropped ship photos had been given a full-frame box, teaching the model that any large blob is a wreck. It was the rock-cluster false-alarm engine.
false-positive rate 0.313 → 0.266
shipwreck precision 0.57 → 0.66
Doubled crab_pot data (900 → 1,600 tiles) to rescue the failing class; rebuilt splits to 80/10/10 with per-class caps.
crab_pot AP 0.118 → 0.193
still far below the 0.25 bar

The decision that took discipline

Two runs and a doubling of data moved crab_pot from 0.118 to 0.193. That is not a data-volume problem — it is a separability problem. The class is small, low-contrast and acoustically ambiguous against seabed clutter. We kept it in training as a hard negative and filtered it out of the product. The four classes that ship are exactly the four hazards the problem statement names.

Run 2 → Run 3 — fixing the data pipeline

Re-tiled AI4Shipwrecks at 50 % overlap with a morphological close so a broken hull reads as one object. The original stride discarded ~90 % of the usable data.
152 → 890 tiles · 329 → 1,978 boxes
shipwreck instances 75 → 1,554
Added the Lee + CLAHE front end (Module 0), applied identically at training and inference so the model never meets an unfamiliar distribution.
precision 0.734 → 0.734
FP rate 0.266 → 0.266 — no change

Why shipwreck AP fell while the model got better

The 50 % overlap re-tile that gave us 12× more shipwreck training data also tripled the shipwreck instances in the test set, adding partial and near-duplicate tiles. The test became harder at the same moment the model got stronger.

The control settles it: running the Run 2 model on the Run 3 test set scores shipwreck 0.278 — below the new model's 0.302 on the same data. On matched data the two are tied, and Run 3 is marginally ahead.

Overall mAP@50 0.641 · mAP@50-95 0.459 at the standard protocol, and precision 0.734 · recall 0.629 at the deployed operating threshold.

Two protocols, and why both belong here

mAP is the area under the whole precision–recall curve, so it is computed with the confidence floor at ~0.001 — the COCO convention every paper in §05 uses. Precision and recall are operating-point numbers, meaningful only at the threshold actually deployed (0.25, ahead of Module 2's per-class gate).

We initially reported mAP computed at conf 0.25, which truncates the curve's low-confidence tail and mechanically depresses AP — and made our comparison to published work unfair to ourselves. Same model, same test set, corrected: mAP@50 0.580 → 0.641, shipwreck 0.302 → 0.370, cylinder 0.424 → 0.517. The run-to-run comparisons in §07 were all measured identically, so that progression is unaffected.

A detection is not a probability

A raw sigmoid output of 0.8 is not "right 80 % of the time". We fit per-class Platt scaling on held-out data so the number an operator sees means what it says. Per-class matters — a single global calibrator made things measurably worse:

Expected Calibration Error, testRawCalibratedOutcome
Run 2 — one global calibrator0.0420.090worse
Run 3 — per-class calibrators0.0520.037better

Combined with the per-class gate, this is what converts raw detections into an operator product: shipwreck precision 0.63 → 0.73 and cylinder 0.58 → 0.75 at the working threshold, with scores that survive scrutiny.

The route in one paragraph

A small, anchor-free detector chosen on published evidence from our own dataset, trained on assembled real survey data with synthesis only where the world offers none, wrapped in a deterministic physics filter and per-class calibration so the confidence means something, exported to a torch-free runtime that already meets its edge latency target on a CPU. Every weak point is measured and has a named remedy. Nothing in it depends on a claim we have not tested.

The geotagging maths

Image row → ping number → the navigation record's timestamp → interpolate the logged (lat, lon, heading). Image column → slant range R. Then, assuming a flat seabed:

slant to ground rangeG = √( R² − H² )     near nadir G → 0 (the "nadir gap"); at far range G → R

The target lies G metres from the track, perpendicular to heading — bearing − 90° for port, + 90° for starboard — reached by a geodesic forward step. This follows the published Yu et al. (2021) formulation; our additions are the header-only XTF parser and the sub-metre validation.

A detection is a search area, not a survey fix

The tow-fish position recovers to < 1 m. But the detection position also depends on the across-track scale, and our two navigation paths placed the same target ~122 m apart. Everything downstream — the dashboard pin, the report, the public map — must carry an uncertainty radius rather than imply metre accuracy we do not have.

12

The edge build

The PS requires offline execution onboard marine drones. An AUV has no GPU and no room for a 1.5 GB PyTorch runtime. We exported to ONNX and measured all three precisions rather than assuming.

PrecisionSizeCPU latencyAccuracy vs PyTorchDecision
FP32 ONNX44.8 MB~90 msidentical — verified on all 850 test tilesshipped
FP16 ONNX22.4 MBn/a on CPU—Jetson GPU target
INT8 ONNX11.5 MB164 ms — slower0.00 precision / 0.00 recall, every classexcluded

Where we went past the literature

The 2026 paper that sets the AI4Shipwrecks detection record assumes INT8 quantization transfers cleanly with "proportional" reductions. We tested it. On faint sonar targets, static post-training quantization collapsed the detector to zero — and ran slower than FP32 on any CPU without VNNI/AVX-512, because the quantise/dequantise nodes cost more than the integer math saves. We publish the broken INT8 file alongside the working ones so the result is reproducible.

The deployment path carries no PyTorch at all — onnxruntime + numpy + opencv, about 210 MB installed against torch's 4.4 GB, and ~50 MB resident against ~1.5 GB just to import torch. Verified end to end: a shipwreck tile scores 91.3 %, auto-confirmed, in 110 ms, with torch and ultralytics both absent from sys.modules.

The ONNX file is not a reduced model — same weights, same architecture, same answers. The choice is entirely about what has to be installed to run it.

Why the CPU baseline matters more than it looks

We already meet the ≤100 ms engineering target on a laptop CPU with no GPU at all. 14

Three operating modes

The same model and the same report schema serve three situations. Only the first exists today.

Mode C — the public debris map

The point of detecting a ghost net is that somebody removes it, or at minimum stops losing gear on it. A net keeps fishing for decades after it is lost. The fisher who needs that information does not have a sonar console — they have a phone, on a boat, often with no signal.

So: a mobile web app showing analyst-confirmed hazards only near the user's live GPS position, with the region cached for offline use at sea, and each hazard drawn as an uncertainty circle rather than a pin. Three gates stand between the database and the public — confirmed-only, a heritage screen, and the uncertainty radius.

Three governance decisions before that goes live

Shipwrecks are frequently protected heritage, and in some jurisdictions war graves. Publishing exact positions can enable looting. Recommendation: coarsen wreck positions by default, gate full precision behind an authenticated authority account.

Suspected ordnance is a safety notice, not a map pin. A mine_cylinder detection is unverified by definition; the primary route should be a notification to the maritime authority, not a public layer.

The map is advisory, not a navigational chart. It supplements official notices to mariners; it never replaces them, and it must say so.

Part VI — scale
15

Scalability

Scaling this system means six different things. Five of them are straightforward because of choices made early. The sixth is the one that actually breaks first, and it is not compute.

Throughput, concretely

The model runs at ~90 ms/tile on CPU with a ~250 MB worker footprint. A four-core VM running four worker replicas sustains roughly 40 tiles/second — far beyond a single survey upload, and orders of magnitude beyond the few pings per second the sonar produces. Scaling is one flag:

docker compose up -d --scale worker=4     # each replica ~250 MB RAM, no GPU

Had we put the model behind its own microservice, each of those replicas would carry a ~5 GB torch image and a per-tile network hop. The torch-free decision is what makes horizontal scaling cheap enough to be uninteresting.

Scaling the public map is a different problem — and an easier one

The operator dashboard serves a handful of analysts. The public map could serve thousands of fishers. Those are separated deliberately: the public endpoint is read-only, unauthenticated GeoJSON, cached at a CDN edge. Readers never touch the application server or the database. A million map views cost the same as one.

What we would do at ten times the data

  • Object storage for imagery instead of a shared volume — uploads and evidence crops move to S3-compatible storage; the database keeps only records and references.
  • Spatial indexing — PostGIS with a GiST index once the bbox query on plain lat/lon columns stops being instant.
  • Per-region model versions — the fine-tuning loop already produces them; this is a registry and a routing rule, not new science.
  • Batch the worker — ONNX Runtime accepts batched input; tiles from one transect can go in groups rather than singly, which is pure throughput at no accuracy cost.
  • Temporal persistence before the queue — the single highest-leverage change, because it attacks the human bottleneck rather than the machine one.

Every weak class is weak for a reason we can point at, every limitation is measured, and every remedy is named.
