What the model actually does

Overall mAP@50 0.641 · mAP@50-95 0.459 at the standard protocol, and precision 0.734 · recall 0.629 at the deployed operating threshold. Confidence is per-class Platt-calibrated — expected calibration error 0.052 → 0.037 — so the percentage an operator sees means what it says.

For context: on AI4Shipwrecks, the dataset behind our shipwreck class, the 2026 state of the art is 0.755 and a vanilla YOLOv8 baseline is 0.716 — both single-class. Human annotators agree with each other only 50–60 % on where a wreck's boundary lies in an acoustic image. Our four-class model on a deliberately harder overlapping split sits inside that band.

Three limits that shape every deployment decision below

  • It does not transfer to an unseen survey without fine-tuning. Near-zero detections on an unfamiliar instrument and seabed. This is documented literature behaviour, and the remedy — fine-tune on a small labelled sample of the operator's own sonar — is designed into the review loop.
  • A detection is a search area, not a survey fix. The tow-fish position recovers to <1 m, but detection position also depends on across-track scale; two navigation paths placed the same target ~122 m apart. Everything downstream must carry an uncertainty radius.
  • ghost_net is trained on synthetic data. No public real ghost-net-in-sonar dataset exists. Treat 0.995 as proof of capability, not field performance.

Why Orin NX 16 GB rather than a Nano. YOLOv8s is small, but the edge computer also carries preprocessing, navigation-data association, the shadow-geometry check, tile buffering and mission logging — plus headroom for the persistence filter and any future model. A Nano stays on the list as a lower-power alternative to benchmark, not as the default.

Why the CPU baseline matters more than it looks

We already meet the ≤100 ms engineering target on a laptop CPU with no GPU at all. The Jetson is therefore about headroom and power efficiency, not about making the system feasible. That is a far more comfortable position than needing the accelerator to hit spec — and it means a degraded-mode fallback to CPU-only inference remains viable.

INT8 stays excluded. Static post-training quantization collapsed the detector to 0.00 precision and recall on every class, and ran slower than FP32 on CPU. FP16 is the Jetson path; the broken INT8 file is published only so the result is reproducible.

04

Three operating modes

The same model and the same report schema serve three different situations. Only the first exists today; the other two are what this dossier plans.

Mode A · built

Demo dashboard

Upload a sonar file from a browser. Detection runs on the server, results stream back live, an analyst reviews and exports. This is the SIH demonstration.

Mode B · designed

Live AUV survey

The model runs on the Jetson inside the vehicle. No connectivity is assumed. Results are stored aboard and synced in bulk on recovery.

Mode C · proposed

Public debris map

Confirmed hazards published to a mobile map with live GPS, so the people who work these waters can see what is around them.

Assumption to verify before quoting

Acoustic modem throughput is not yet researched for our configuration. The "~80 bytes/detection" figure above is a design target derived from a packed contact record (class id, confidence, lat/lon, ping reference) — not a measured link budget. Treat it the same way the reference report treats the 5 Hz cadence: a working assumption that sizes the design and must be replaced with a measurement.

Mode A — the demo dashboard

What we show at SIH, and the foundation everything else is built on. An operator uploads a sonar file and watches detections appear on a map as each tile completes.

The review bands are decided by the model layer, not the UI: ≥ 80 % auto-confirmed, 30–80 % queued for a human, < 30 % dropped before it ever reaches the operator. That is what makes the queue short enough to actually work through — and it is the same mechanism that feeds Mode C, since only analyst-confirmed detections are ever published.

06

Mode C — the public debris map

The point of detecting a ghost net is that somebody goes and removes it, or at minimum stops losing gear on it. Detection that stays inside an operator console has not finished the job.

A ghost net keeps fishing for decades after it is lost. A fisher who knows one is there avoids it; a recovery NGO who knows where it is can go get it; a diver who knows a wreck's position can plan around it. None of those people have access to a sonar console — they have a phone, on a boat, often with no signal.

What the page does

  • Shows what is around you. The browser's geolocation API gives the phone's position; the map centres there and loads confirmed hazards within the visible box. Nearest few are listed with distance and bearing.
  • Works without signal. A service worker caches the map tiles and the hazard layer for a chosen region before departure. This is the feature that decides whether it is useful at sea or just useful in port.
  • Shows uncertainty honestly. Each hazard renders as a circle sized to its positional confidence — never a pin implying metre accuracy we do not have.
  • Optional proximity alert. A configurable radius warns when you are closing on a known snag hazard.
  • Reports back. A "seen / not there / recovered" control lets users close the loop, feeding the same review queue an analyst works.

Three governance decisions to make before this goes live

Shipwrecks are frequently protected heritage. Publishing exact positions can enable looting of archaeological sites and, in some jurisdictions, of war graves. Recommendation: withhold or coarsen wreck positions by default, and gate full precision behind an authenticated authority account.

Suspected ordnance is a safety notice, not a map pin. A mine_cylinder detection is unverified by definition. If published at all it must read as "suspected object — do not approach — report to the maritime authority", and the primary route should be a notification to that authority rather than a public layer.

The map is advisory, not a navigational chart. It carries no hydrographic authority and must say so plainly. It supplements official notices to mariners; it never replaces them.

The web stack

One repository, one docker compose up, five services. The model is a library imported by the worker — there is no ML microservice, and no network hop per tile.

RuntimeInstalled sizeRAM to importAccuracy
torch + ultralytics not used~4.4 GB~1.5 GBidentical
onnxruntime shipped~210 MB~50 MBidentical

The ONNX file is not a reduced model — same weights, same architecture, verified detection-for-detection against PyTorch on all 850 test tiles. The choice is entirely about what has to be installed to run it. best_detector.pt stays in the repository for retraining; the serving path never touches it.

Deployment roadmap

Four phases. Each one is independently demonstrable, and nothing in a later phase invalidates an earlier one.

PhaseScopeStackStatus
1 · Demo
SIH		 Upload → detect → map → review → export. Single operator, single machine. One VM (4 vCPU / 8 GB). docker compose up. Caddy or nginx + Let's Encrypt. All five services on one box. wiring now
2 · Pilot Multi-user, persistent surveys, the public map goes live behind its gates. Managed PostgreSQL; object storage for uploads; the public GeoJSON endpoint cached at a CDN; PWA on static hosting. Worker replicas scale independently. planned
3 · Field Model on the vehicle. Autonomous survey, bulk sync on recovery. Jetson Orin NX 16 GB, FP16 TensorRT engine, torch-free stack in a pressure/thermal enclosure. Ship server runs the same compose stack for reprocessing. needs benchmark
4 · Loop Confirmed detections become training data; the model improves per operator. Fine-tuning job from the review queue; per-survey model versions; A/B against the frozen baseline. designed

docker compose up -d --scale worker=4

Why one box is not a compromise

The model runs at ~90 ms/tile on CPU with a ~250 MB worker footprint. A 4-core VM running four worker replicas processes roughly 40 tiles/second of wall-clock throughput — far beyond what a demonstration, or a single survey upload, requires. Splitting the ML onto its own server would add a deployment, a failure mode and a per-tile network hop while buying nothing we need.
