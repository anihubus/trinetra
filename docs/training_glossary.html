Reading the training log

Every number and word that scrolls past while the detector trains, defined in plain language — plus flow diagrams of the training loop, the model itself, and how the accuracy scores are actually computed.

01 The two lines that repeat every epoch

During training, YOLO prints one progress line while it learns from the training set, then one validation line after it checks itself on the held-out val set. This is the real output from Run 2, epoch 8:

     Epoch   GPU_mem   box_loss   cls_loss   dfl_loss  Instances   Size
     8/120     3.48G      1.511       8.58      1.573         11        640: 100% 330/330  4.1it/s  1:20
               Class   Images  Instances    Box(P       R     mAP50   mAP50-95)
                 all       712       1018     0.589     0.532     0.534      0.294

Progress line — how the learning is going

Epoch 8/120
Epoch = one complete pass over every training image. We plan up to 120; training can stop earlier (see patience).
GPU_mem 3.48G
Video memory the run is using on the RTX 4050. The card has ~6 GB, so 3.48 GB leaves comfortable headroom — batch size could go higher.
box_loss 1.511
How wrong the predicted box positions and sizes are, averaged over the epoch. Lower = tighter boxes. Trends down as training proceeds.
cls_loss 8.58
How wrong the predicted class labels are. Still high at epoch 8 — it should fall below ~2 within the first 30–40 epochs. If it stays high, the classifier is still confusing classes (crab-pot is the usual culprit).
dfl_loss 1.573
Distribution Focal Loss — how fuzzy the box edges are. YOLOv8 predicts each edge as a probability spread over positions; this loss sharpens that spread to a confident single location.
Instances 11
Number of labelled objects in the last batch shown (not the whole epoch). Just a sanity readout — varies batch to batch.
Size 640
Every image is resized to 640×640 pixels before it enters the model.
330/330
Batches (iterations) per epoch = training images ÷ batch size ≈ 4,900 ÷ 16. The bar fills as batches complete.
4.1it/s
Iterations per second — 4.1 batches (65 images) processed every second on the GPU.
1:20
Wall-clock time this epoch took (1 min 20 s). ×120 ≈ the full run.

Validation line — how good it actually is

Run on the val set with no learning. One row per class; all is the average across classes.

Images 712
Val images checked this epoch.
Instances 1018
Total labelled objects across those images.
Box(P 0.589
Precision — of the boxes the model drew, 59% were real objects; 41% were false alarms.
R 0.532
Recall — of the objects that were really there, the model found 53%; it missed 47%.
mAP50 0.534
Mean Average Precision at IoU 0.50 — the headline accuracy score (0–1). Rewards finding objects and boxing them with at least 50% overlap. Averaged over all classes.
mAP50-95 0.294
The same score averaged over ten stricter overlap thresholds (0.50, 0.55, … 0.95). Much harder — it measures how precisely the boxes fit, not just whether the object was found.

Is epoch 8 on track?

Yes. Run 1 hit mAP50 0.58 around epoch 10; Run 2 is at 0.53 at epoch 8 with a harder, crab-pot-heavier dataset — same trajectory. Watch two things in results.png afterward: cls_loss should keep falling steeply, and val mAP50 should push past 0.60 and then flatten. If mAP50 flattens below ~0.55, the data mix is the ceiling, not the training time.

04 The three losses — what each one grades

A "loss" is a single number saying how wrong a prediction is; training = making it smaller. YOLOv8 grades three separate things and adds them up.

06 How the accuracy scores are computed

Every number on the validation line comes from comparing predicted boxes to ground-truth boxes. Two steps: decide which predictions "count as a hit", then turn the hit/miss tally into a score.

07 Everything else you'll see in our training

TermWhat it means for us
transfer learning / fine-tuningWe don't start from zero. We load yolov8s.pt, already trained on millions of everyday photos (COCO), and re-train it on sonar. The early layers ("find edges and blobs") are already useful; we mostly re-teach the later layers.
backbone / neck / headThe three parts of the model. Backbone = extract features. Neck = combine features at different sizes. Head = output the actual boxes and class scores.
parameters (11.1M)The individual numbers inside the model that get adjusted during training. "11.1M params" = a small model, deliberately — it has to fit 6 GB VRAM and run fast on edge hardware.
GFLOPs (28.4)Billions of math operations to run the model on one image. Lower = faster. 28 is light — hence 3.9 ms per frame.
layers (73, "fused")Depth of the network after an inference-time optimisation that merges adjacent operations. Cosmetic readout.
batch size (16)Images processed together before one weight update. Bigger = smoother, steadier learning but more VRAM.
learning rate (lr0 0.001)How big a step the optimizer takes each update. Too big = unstable; too small = slow. We warm it up for 3 epochs, then decay it toward zero (cosine schedule) so late training makes fine adjustments.
optimizer (AdamW)The rule that turns gradients into weight changes. AdamW adapts the step size per-weight and is a safe default for fine-tuning on a few thousand images.
momentum / weight decayOptimizer knobs. Momentum = keep rolling in a consistent direction (smooths noise). Weight decay = gently pull weights toward zero (discourages memorising).
gradientFor each weight, the direction and amount to change it to reduce the loss. Produced by the backward pass.
AMP / mixed precisionDoing most math in 16-bit instead of 32-bit. Roughly halves VRAM and speeds training with negligible accuracy cost. On by default.
overfittingModel memorises the training images instead of learning general patterns — train score keeps rising while val score stalls or drops. Run 1 did not overfit.
early stopping / patience (25)If val mAP50 doesn't improve for 25 straight epochs, stop — further training is just wasting time or starting to overfit.
augmentationRandomly altering training images each epoch so the model sees more variety: mosaic (stitch 4 images), mixup (blend 2), brightness jitter, rotation, horizontal flip, erasing (blank a patch — mimics sonar dropouts). close_mosaic 15 = turn mosaic off for the last 15 epochs so it finishes on clean images.
class weight / cls gain (1.66)We auto-raise the penalty for misclassifying rare classes (shipwreck, cylinder) so they aren't ignored in favour of the common one.
ground truth / labels / annotationsThe human- (or, for ghost-net, procedurally-) drawn boxes we treat as correct. Everything is scored against these.
confidence scoreThe model's raw 0–1 certainty on a detection. Module 2 later re-calibrates this into an honest probability.
conf threshold (0.25)Minimum confidence to keep a detection. Lower → more found (higher recall) but more false alarms (lower precision).
NMS + IoU threshold (0.7)Non-Max Suppression removes duplicate boxes on one object: if two boxes overlap more than 0.7 IoU, keep only the higher-scoring one.
train / val / testTrain = the model learns from these. Val = checked every epoch to steer training and pick best.pt (model sees the scores, indirectly). Test = touched once at the end for the honest number.
checkpoint (best.pt / last.pt)Saved model files. last.pt = the most recent epoch. best.pt = the epoch with the highest val mAP50 — this is the one we ship.
convergence / plateauWhen the loss and val mAP stop meaningfully changing epoch to epoch — the model has learned what this data can teach it.
confusion matrixA grid of true class vs predicted class. The diagonal = correct; off-diagonal = which classes get mistaken for which (or for "background").
inference speed (3.9 ms / ~250 FPS)Time to run the trained model on one image. Matters for the edge / AUV deployment claim.
